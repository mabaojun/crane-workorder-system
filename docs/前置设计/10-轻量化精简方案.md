## 1. 决策摘要

本方案回应「系统规模小、并发极低，现有架构是否冗余、能否更轻量化」的评审。四项决策如下。

- 决策一：保留前后端分离 + Spring Boot 分层单体的架构方向，不更换技术栈。分层单体本身就是轻量形态，功能复杂度来自 PRD 而非框架。
- 决策二：移除 Redis。登录态失效改由 `sys_user.force_logout_at` 承担，短信验证码与幂等键落 MySQL 新表。
- 决策三：定时任务并入应用进程，撤销独立 `crane-scheduler` 容器；Docker 容器由 6 个减为 4 个。
- 决策四：任务包按 MVP 分级执行，不砍功能，收本期范围。

四项决策均不触碰 01 §6.3 枚举、03 的接口路径与错误码，不影响 04–07 各通道页面与权限设计。

## 2. 规模画像与承载力评估

以下规模数据来自项目实际盘点和 PRD 5.4 的功能边界，承载评估标注 [Expert judgment]。

| 维度 | 现状 |
|---|---|
| 司机 | 不超过 10 人 |
| 车辆 | 10 台 |
| 客户 | 数十家 |
| 管理人员 | 2 人（含原总监职责，合并为统一管理员） |
| 财务人员 | 1 人 |
| 工单量 | 每日个位数 |
| 在线并发 | 全端最坏场景不足 60 人同时在线，接口峰值 QPS 低于 5 |

按上述规模测算：年工单量在 2000–3000 量级，相关派生记录（打卡、通知、异常、冲突提醒）年增量百万行以内，单表千万级与峰值 30 并发的前提（01 §7）留有余量。缓存命中收益趋近零，分布式锁无需求（单实例部署），高可用目标维持 99% 即可。

结论：当前规模下，系统压力不构成瓶颈，冗余风险来自「为不存在的压力引入组件」，而非架构形态本身 [Expert judgment]。

## 3. 逐组件决策

| 组件 | 决策 | 理由 |
|---|---|---|
| 前后端分离 + monorepo（admin / screen / mobile） | 保留 | 已选型；uni-app 一套源码编译 H5 与小程序，实际 3 个前端应用 |
| Spring Boot 3 分层单体 | 保留 | 常规单体形态；事务、定时调度、鉴权、报表生态成熟，10 人团队维护成本最低 |
| MySQL 8 | 保留 | 工单 / 车辆 / 财务数据必须持久化；社区版免费（见第 7 节） |
| Redis | 移除 | 规模小、无缓存收益、单实例无分布式锁需求；中间态改落 MySQL |
| 独立 scheduler 容器 | 并入 app | 定时任务由应用内 Spring 调度承担，单实例不重复执行 |
| Nginx | 保留 | HTTPS 终结、静态资源托管、反向代理，成本极低 |
| 31 张表 / 68 个接口 | 保留，按 MVP 分级 | 数量由 PRD 功能决定；按第 6 节分级执行 |
| 26 个任务包 | 重排执行顺序 | 不砍任务，标 MVP 优先级 |

## 4. 移除 Redis 的落库替代方案

去掉 Redis 后，原由它承担的职责逐一落到 MySQL，均以既有或新增表实现 [Expert judgment]。

| 原职责 | 替代方案 | 承载 |
|---|---|---|
| 登录态（可强制下线） | JWT 无状态校验 + 校验用户 `force_logout_at`，早于该时间的令牌失效 | `sys_user.force_logout_at`（已有字段） |
| 短信验证码 | 发送前写入验证码表，校验时读取并比对，记录发送频次与已使用标记，天然可追溯 | 新增 `sys_sms_code` |
| 写接口幂等键 | 幂等键表唯一索引去重，窗口内重复请求返回首次结果 | 新增 `sys_idempotency` |
| 定时任务分布式锁 | 单实例部署下同一 Spring 调度任务不并发执行；如后续多实例再引入锁 | 无需承载 |
| 业务缓存 | 数据量小，直接查库 | 无需承载 |

落库替代带来三点收益：验证码与幂等键具备可追溯记录，满足冲突提醒与审计需求；去掉缓存一致性维护负担；部署链路少一个依赖服务。

## 5. 部署精简（容器 6 变 4）

Docker Compose 服务由 6 个减为 4 个：

| 调整前 | 调整后 | 说明 |
|---|---|---|
| crane-nginx | crane-nginx | 保留 |
| crane-app | crane-app | 内嵌定时任务调度 |
| crane-scheduler | （并入 crane-app） | 撤销独立容器 |
| crane-mysql | crane-mysql | 保留 |
| crane-redis | （移除） | 中间态落 MySQL |
| crane-backup | crane-backup | 保留 |

配套变更：删除 `REDIS_*` 环境变量、`crane-redis-data` 卷、63791 端口映射、Redis 资源限额与健康探针；基础镜像锁定清单去掉 Redis；发布与回滚流程去掉缓存项。具体修订见文档 08。

## 6. MVP 范围分级

不砍功能，仅分级执行，任务包编号与文档 09 一致 [Data-backed：09 §4]。

| 级别 | 阶段与任务 | 范围 |
|---|---|---|
| MVP 必选 | 阶段 1–2（T-00、T-10 至 T-16）、阶段 4（T-20 至 T-22） | 工程骨架、认证与账号权限、员工车辆档案、需求单、工单状态机、派单接单、打卡工时、异常上报、后台框架与登录、需求单与工单、档案与账号权限 |
| MVP 必选 | 阶段 5（T-30、T-31、T-33） | 移动端骨架与登录、司机端工单操作、客户端与 H5 通道 |
| 二期 | 阶段 3（T-17 至 T-20B）、阶段 4（T-23、T-24）、阶段 5（T-32、T-34）、阶段 6（T-40） | 变更审批、冲突提醒、通知双通道、统计与 AI 适配、系统配置、审批与冲突提醒中心、统计与 AI 前端、移动端冲突处置、管理员移动端、数据大屏 |
| 收尾 | T-50、T-60、阶段 9 | 联调测试、容器化部署、验收交付 |

MVP 验收标准：需求单转工单、派单、接单、执行、结单核心链路闭环，后台与司机 / 客户移动端可用。二期功能在核心闭环验证通过后逐项叠加。

## 7. 成本说明

MySQL 采用 Docker 官方 `mysql:8` 社区版镜像，GPL 协议开源免费，自建不产生授权费用 [Data-backed：MySQL Community License]。收费的两类路径均未采用：MySQL Enterprise 企业版需要商业授权；云厂商托管数据库服务按规格付费。本方案唯一实际成本是云服务器租用费与存储，与数据库选型无关。

## 9. 决策记录

| 备选方案 | 评估 | 结论 |
|---|---|---|
| 更换更轻技术栈（Flask / Node 单体） | 业务逻辑不会因换栈减少；丢失 01–09 锁定的契约一致性、Spring Boot 的事务与调度生态、AI Agent 提示词最稳定的基准 | 不采用 |
| 保留 Redis 不动 | 多一个容器与依赖、多一层缓存一致性负担，收益趋近零 | 不采用 |
| 去掉 Nginx，由应用直接托管静态资源 | 可省一容器，但失去 HTTPS 终结、静态资源缓存与反向代理的灵活性，成本极低 | 不采用 |
| 微服务化 | 与规模严重不匹配，纯增运维成本 | 不采用 |
